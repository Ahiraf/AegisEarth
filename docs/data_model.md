# Data model and artifact contract

The new baseline migration is `cosmic_0001`. It targets a fresh `cosmic_motion` database. It is not a
conversion migration for another product. No live database was reset as part of restructuring.

## Implemented schema foundation

| Table | Identity / relations | Main responsibility |
| --- | --- | --- |
| observations | Internal UUID string; unique collection + release + provider product ID | Discovery metadata, source URL, sky position, original MJD/scale and source metadata |
| analysis_runs | UUID; status and idempotency key | Config, pipeline version, request hash, future worker lease and sanitized failure code |
| analysis_inputs | Run FK + observation FK; unique ordinal within run | Ordered reference/science/sequence inputs without JSON-only pseudo-FKs |
| stage_executions | UUID; run FK; unique stage + attempt per run | Stage lifecycle, timing and QC metrics |
| model_versions | UUID; unique name + version | Classical/CNN/Siamese identity, weights reference/checksum, evaluation and calibration state |
| candidates | UUID; run FK; optional model FK | Candidate class, celestial position, displacement, score kind and evidence |
| artifacts | UUID; optional run/observation FK; unique storage key | Bytes location, content type, checksum, size, provenance and publication flag |

The model registry imports every feature's models for Alembic discovery. Constraints cover initial
coordinate ranges, run state, input ordering, score range, candidate class and artifact size. Add stricter
stage/score/calibration constraints with the corresponding services; this is not the final production schema.

## Observation identity and scientific metadata

- Provider ID identifies a particular image/product; release/processing version remains part of identity.
- A repeat observation is a separate record even when it covers the same sky position.
- Preserve source metadata verbatim/reference with payload checksum when discovery is implemented.
- Required enrichment before comparison: footprint, observation start/end and scale, normalized times,
  detector/filter, local wavelength/bandwidth, pixel scale/WCS, calibration version, access checksum and flags.
- RA is [0,360) degrees and Dec [-90,90]. Pixels are not interchangeable with celestial coordinates.
- Store original MJD as a precision-preserving numeric representation and retain the time-scale label.
  No timestamp may silently acquire a UTC label. PostgreSQL timestamptz is for representable UTC instants;
  keep original/ISO scientific representations for leap seconds and any provisional conversions.

## Candidate evidence contract (target)

Each candidate must eventually expose:

1. Candidate/run IDs, hypothesis class and explicit candidate status.
2. Per-epoch celestial and image coordinates, centroid errors and observation timestamps.
3. Displacement in arcsec, position angle and time separation where measured; angular rate only with units
   and uncertainty. No unsupported physical distance, orbit or threat estimate.
4. Source/residual SNR, morphology, flag/edge proximity, registration residual and wavelength/PSF context.
5. Ranking method/version, raw score, score kind and calibration reference if applicable.
6. Original/aligned/difference stamps and overlay references with pixel-origin/display transforms.
7. Explanatory codes and warnings such as masked-pixel contamination, weak association or missing epoch.

The initial JSON evidence/config/provenance columns allow evolution during research. Before accepting
public results, define/version Pydantic envelopes and migrate commonly queried scientific fields to indexed
columns. Do not depend on undocumented JSON keys as a permanent external API.

## File and model storage

- Raw FITS, processed arrays, PNG previews and model weights are stored outside PostgreSQL.
- Object keys are generated by the backend. Callers use opaque artifact IDs, not paths or arbitrary URLs.
- Record SHA-256, byte size, media type, source/product IDs and transformation lineage.
- Publish only artifacts referenced by an atomically completed manifest; retain partial data privately for
  bounded debugging and garbage-collect abandoned files according to the retention policy.
- Store ML weights in an approved immutable format/location. Do not load user-supplied pickle/checkpoints.
- Repository excludes FITS/weights/cache files. Small synthetic arrays should be generated in tests;
  real curated data need a manifest, permitted-use review and durable download location.

## Planned schema extensions by milestone

| Milestone | Add / tighten |
| --- | --- |
| Discovery | Fielded footprint/time/wavelength metadata, source snapshot/checksum, indexes |
| Durable jobs | Caller-scoped idempotency, attempts/heartbeat/deadline, cancellation and retry policy |
| Scientific stages | Versioned QC envelopes, validated output artifact relations and timestamps |
| Candidate serving | Detection/association tables or indexed fields as query needs establish |
| ML | Dataset/label manifests, model card, evaluation/calibration references and deployment approval |
| Sequence tracking | Per-epoch detections, association edges, tentative track and fit uncertainty |

Production retention is proposed as curated demo artifacts retained for the release and temporary failed
outputs deleted after seven days. Confirm budget/source terms before activation. Backups must cover
database metadata and durable object references; test restore consistency of both.
